## Failures and fixes

Every failure seen while building and running the suites, why it happened, and what was changed. **Application** means a defect in Reading Pal itself; **Test** means a problem in the test code.

| Case | Where | What failed | Why | What was fixed |
| --- | --- | --- | --- | --- |
| ACC-04 | Application | Run 1: the admin saw "Failed to revoke user access. Please try again." and the member stayed active. | frontend/src/pages/AdminUsersPage.tsx sent the revoke request to a hard-coded http://localhost:5000. The User Service runs on 5050 locally (macOS AirPlay holds 5000) and there is no localhost on Azure, so the request never reached it. Accept and Reject on the same page use the configured address. | Branch fix/revoke-member-url, commit f6e9b26 ("YRP-150 send the revoke request to the configured User Service"): the request now uses API_BASE_URL. Passed in run 2 and in three separate reruns. Until that branch is merged, ACC-04 still fails on develop. |
| ACC-04 | Test | While developing: an UnhandledAlertException instead of a readable failure. | The failure alert opened while the test was still checking the page, and any page query throws while an alert is open. | The wait checks for an alert first and the test fails with the alert's text. |
| REG-09 | Test | While developing: the names never stacked at phone width. Run 1: the two name fields were 312 px and 313 px from the top. | Headless Chrome will not make a window narrower than about 500 px, so the 420 px phone layout never applied. Later, sub-pixel rounding put side-by-side fields 1 px apart. | Phone widths are emulated through the Chrome DevTools protocol (Browser.Resize), and "side by side" allows 2 px. Passed three reruns, run 1's User rerun and run 2. |
| SRCH-07 | Test | While developing: StaleElementReferenceException. | The result list re-renders as results arrive, so rows Selenium had found were replaced before it read them. | Result titles are read in one JavaScript call. |
| ADMBOOK-06 | Test (planned expectation was wrong) | While developing: expected the title to stop at 200 characters; all 250 were accepted. | The Add book form has no maxLength (the Edit form has). Recorded as finding 8 in TEST-PLAN.md. | The case now checks what really happens: the server refuses the overlong title ("Failed to add book. Please verify your inputs and try again.") and the Edit form stops at 200. |
| ADMAUTH-02, -03, -07, -08 | Test | While developing: the author's row was never found. | An author without a portrait shows their initial in front of the name, so the cell text was "EE2E Author…", not an exact match. | Rows are matched on the name contained in the first cell. ADMAUTH-03 also read the dialog text before it rendered; it now waits for the text. |
| ADMLIST-01 | Test | While developing: the "Created …" message never appeared. | Creating a list opens its contents editor at once, and the page hides its message while a dialog is open. | The test expects the editor, closes it, then checks the message. |
| RES-02 | Test | While developing: StaleElementReferenceException on the author page. | The shelf re-rendered between finding it and reading the button inside it. | The test waits for the Pending button itself. |
| ADMRES-05 | Test | While developing: set-up failed with "Book is currently unavailable for reservation." | The second member reserved after the only copy was lent, which the service correctly refuses. | Both members reserve while the copy is on the shelf, then the first request is accepted. |
| NOTIF-12, -13, -14 | Test | While developing: unread counts were one higher than expected, and an item stayed in the unread list after being read. | The member could also receive a "New in the catalogue" notice for the test's own book: the book and the member's approval happened within the same second. | The tests match the rejection notification's own text and take expected counts from the API. |
| ADMLIST-10 | Test (label only) | Not a failure: the code labelled the case Unhappy while TEST-PLAN.md says Happy. | Mismatch between plan and code. | The code now matches the plan, giving the planned 112 happy and 75 unhappy cases. |
