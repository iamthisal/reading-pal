## 6. Selenium E2E tests

**Status: passing — 8/8 against the deployed site.** 8 tests across 6 files in `tests/selenium-tests/LendingService.Selenium`, covering reserve, accept, reject, return, user-cancel, and the admin history filter, following the existing repo pattern (`WebDriverHelper`, real browser, real full stack). Target environment is env-var driven (`SELENIUM_FRONTEND_URL`, `SELENIUM_ADMIN_EMAIL/PASSWORD`, `SELENIUM_USER_EMAIL/PASSWORD`) — the same suite runs against a local docker-compose stack or the deployed site with no code changes.

**Run 1 — local docker-compose stack.** Two real, reproducible bugs were found and fixed along the way:

1. **Frontend bug** (`frontend/src/components/ProtectedRoute.tsx`): it checks `user` on first render, but `AuthContext` only decodes `user` from the stored JWT inside a `useEffect` that fires *after* that render — so a hard page load of any protected route redirects to `/login` even with a valid token already in `localStorage`. Worked around in the test suite by navigating via sidebar link clicks (as a real signed-in user would) instead of direct URL loads. **This is a real application bug worth fixing separately from the test work** — anyone who refreshes the browser or opens a bookmark to e.g. `/admin/books` while logged in gets bounced to the login screen.
2. **Test-harness bug**: a `.Clear()`/native-setter script for React-controlled inputs was reading the property descriptor off the wrong JS realm's prototype, throwing `Illegal invocation`. Fixed by walking the element's own prototype chain instead. A related fix: the Add Book form's Genre field is a `<select>` populated from Genre Management, not free text — the suite now creates a genre through the real UI first and selects it via `SelectElement`, rather than typing into a field that was never going to accept arbitrary text.

Local Run 1 was interrupted before a final pass/fail count was captured with all of the above fixes applied together — the genre-select fix specifically was verified working for the first time during Run 2 below, against the deployed site, not re-confirmed locally afterward. Since it's the same code path either way, there's no reason to expect a different outcome locally, but that's an expectation, not a verified number — no local "X/Y passed" is claimed here.

**Run 2 — deployed site** (`https://polite-water-0c0e68a00.3.azurestaticapps.net`). Verified first that the deployment is wired correctly (all 3 backend App Services healthy, and the built frontend bundle really does call the deployed lending-service rather than `localhost`). The deployed database had no "User"-role test account, so one was registered and approved via the same API calls used locally (a dedicated test member account), confirmed logging in successfully before running anything.

The 4 core lifecycle tests (Reserve, Accept, Reject, Return) were run first:

- First attempt: 3/4 passed, 1 timeout — the very first request of the run hit Azure App Service cold-start latency (the book-creation step took longer than the 25s wait budget). Re-running that one test alone immediately afterward passed in 8s, confirming it was cold-start, not a logic issue.
- Wait budget raised from 15s → 25s to give the deployed site's real network latency more headroom, and two waits were hardened (waiting for the "Manage Genres" button and the new genre's `<option>` element explicitly, instead of assuming they're already there).
- Clean re-run: 4/4 passed in 43s.

The remaining 4 (Reserve→admin-queue check, user-cancel, both history-filter tests) were then run:

- First attempt: 3/4 passed, 1 failed with `Assert.NotEmpty() Failure: Collection was empty` on both history-filter tests when run separately — a real bug in the test, not the app: the status filter is client-side React state, and `AssertEveryVisibleRowHasStatus` was checking the DOM immediately after `SelectElement.SelectByText()` with no wait for that state update to actually commit and re-render. Fixed by waiting for the table (or its empty-state message) to reach a stable end state before asserting, rather than checking synchronously. Re-run after the fix: 2/2 passed.

**Final full-suite run, after warming up all 3 deployed services first (confirmed sub-second health-check responses to rule out cold start): 8/8 passed in 1m11s.** No tests were skipped or left unverified.

**A further 7 tests were added afterward** to close coverage gaps identified during a review of this suite (role-boundary enforcement in the UI, a reservation edge case, and the user's own borrowing/fine views) — run against the local docker-compose stack rather than the deployed site, since one of them needs direct database access the deployed site doesn't expose. ## 7. JMeter performance tests

**Status: executed.** JMeter 5.6.3 installed via `winget` (`DEVCOM.JMeter`, hash-verified installer, plus its `Microsoft.OpenJDK.21` dependency). `tests/performance-tests/lending/lending-load-test.jmx` covers the 4 endpoints named in `CLAUDE.md`:

- `POST /api/reservations` (TG1 — as the regular test user)
- `POST /api/reservations/{id}/accept` (TG2 — as admin; first does `GET /api/reservations/pending` and extracts whatever reservation is actually first in the queue, so it exercises a real id rather than a hardcoded one)
- `GET /api/my-borrowings` (TG3 — as the regular test user)
- `GET /api/reservations/pending` (TG4 — as admin)

A `setUp Thread Group` logs in once as both accounts against `user-service` and promotes each JWT to a JMeter property, which an HTTP Header Manager attaches as `Authorization: Bearer ...` on every sampler in TG1–TG4. Thread count, ramp-up, loop count, hosts/ports, and both accounts' credentials are all overridable via `-J` (e.g. `-JTHREADS=50`). Every sampler carries an assertion checking it returns the status code its controller action is actually documented to return.

```
jmeter -n -t tests/performance-tests/lending/lending-load-test.jmx -JTHREADS=10 -JRAMPUP=5 -JLOOPS=10 -l tests/performance-tests/lending/jmeter-results/results.jtl -e -o tests/performance-tests/lending/jmeter-results/report
```

(Before running, one genre and one book — restocked with 100,000 copies to survive repeated runs — were seeded directly via the Inventory API, so TG1's reservation requests always have a real book to reserve against instead of running against a fresh, empty catalogue.)

**Result: 10 threads × 10 loops, 502 requests in ~7s (~68 req/s aggregate). 0 errors (0.00%).**

| Sampler | Requests | Errors | Mean | p90 | Throughput |
|---|---|---|---|---|---|
| `POST /api/auth/login` (setup, both accounts) | 2 | 0 | 64–171 ms | — | — |
| `POST /api/reservations` | 100 | **0 (0%)** | 103 ms | 157 ms | 17.7/s |
| `GET /api/reservations/pending` | 200 | **0 (0%)** | 66 ms | 101 ms | 32.9/s |
| `GET /api/my-borrowings` | 100 | **0 (0%)** | 80 ms | 128 ms | 18.9/s |
| `POST /api/reservations/{id}/accept` | 100 | **0 (0%)** | 125 ms | 255 ms | 17.1/s |
| **Total** | **502** | **0 (0.00%)** | 88 ms | 147 ms | 68.6/s |

**On the Accept endpoint specifically**, TG2 deliberately runs 10 concurrent admin threads that each independently `GET /pending` and accept whatever reservation is *first* in the queue — so many threads race to accept the *same* reservation on purpose, to exercise the concurrency control under contention:

- 20× `200 OK` — the number of *distinct* reservations that actually existed to be accepted; one thread per reservation won the race.
- 60× `409 Conflict` — "Only pending reservations can be accepted. Refresh the queue." `ReservationsController.Accept`'s optimistic-concurrency check correctly rejecting a second accept on an already-processed reservation.
- 20× `503 Service Unavailable` — "Inventory checkout could not be confirmed." The same contention one layer down, in Inventory Service's own concurrency token on `AvailableCopies`.

All three are treated as passing by a `JSR223Assertion` on that sampler that checks the response code is one of `200`/`409`/`503` and explicitly sets `SampleResult.successful` accordingly — a plain `ResponseAssertion` cannot do this, since JMeter's HTTP sampler marks any 4xx/5xx response as a failed sample at the transport level before any assertion runs, and a `ResponseAssertion` can only add a failure on top of that, never clear one. Any status outside that set (401/403/404/500) still fails the sampler and the run. Full per-request data, including the assertion detail, is in the dashboard.

Per `CLAUDE.md`, this dashboard should be kept for a local-vs-deployed comparison once the service is on Azure — re-run the identical command with `-JLENDING_HOST=<azure-host> -JLENDING_PORT=443` (and adjust protocol) against the deployed URL and keep both `report/` directories.

## 8. Defects found in application code during testing

Everything below is a genuine defect in the application's own code (`lending-service` or the frontend) surfaced by this testing pass — not a bug in the test scripts themselves, and not expected/correct behavior. Test-harness-only issues are listed separately at the end of this section for completeness, since they are not application bugs.

### 8.1 Frontend: `ProtectedRoute` logs a valid, logged-in user out on a hard page load
**File:** `frontend/src/components/ProtectedRoute.tsx`
**Found in:** Selenium E2E testing, §6 (Run 1, local stack)
**Severity:** Medium — real user-facing defect

`ProtectedRoute` checks the `user` value from `AuthContext` on its very first render, but `AuthContext` only decodes `user` from the JWT stored in `localStorage` inside a `useEffect`, which runs *after* that first render. On a full page load — browser refresh, opening a bookmark, pasting/sharing a direct URL — the first render still sees `user === null` and the guard redirects straight to `/login`, even though a valid, unexpired JWT is already sitting in `localStorage`.

**Reproduction:** log in → navigate to any protected route (e.g. `/admin/books`) → refresh the browser (or open that URL directly in a new tab) → bounced to `/login` despite being authenticated. The JWT itself is fine and still works against the API; this is purely a client-side routing-guard timing bug.

**Impact:** any user who refreshes the page, bookmarks a page, or reopens a shared link while logged in gets force-logged-out from the UI's perspective.

**Status:** **not fixed.** The Selenium suite worked around it (navigating via sidebar link clicks instead of direct URL loads) rather than patching application code, since code fixes were out of scope for this QA pass. Recommended fix: gate rendering on an `isLoading`/`isInitialized` flag that the `useEffect` sets once the JWT decode completes, instead of branching on `user` alone.

This bug surfaced a second time while adding the 7 newer Selenium tests (`final_selenium_test_results.md`): a `Driver.Navigate().Refresh()` call in an early draft of `TC_FINE_001` hit it directly and had to be replaced with a wait for the page's own 10-second polling refresh instead of a hard reload.

### 8.2 Dependency: 2 moderate-severity vulnerabilities in the JWT stack
**Found in:** Security/dependency scan, §5
**Severity:** Moderate (per advisory)

`Microsoft.AspNetCore.Authentication.JwtBearer` 8.0.0 transitively pulls in `Microsoft.IdentityModel.JsonWebTokens` 7.0.3 and `System.IdentityModel.Tokens.Jwt` 7.0.3, both flagged under [GHSA-59j7-ghrg-fj52](https://github.com/advisories/GHSA-59j7-ghrg-fj52). Full output in `security-scan-lending.txt`.

### 8.3 Backend: JWT config in `Program.cs` can't be overridden after host build (testability characteristic, not a production bug)
**File:** `services/lending-service/Program.cs`
**Found in:** Integration test development, §3

`Program.cs` reads `Jwt:Key`/`Jwt:Issuer`/`Jwt:Audience` out of `IConfiguration` into local variables at top-level-statement time, during host *build*. Anything that tries to override those three keys afterward — e.g. `WebApplicationFactory<Program>.ConfigureWebHost(...).ConfigureAppConfiguration(...)` in a test host — is silently ignored, because the values were already copied out before the override is applied. This isn't a production defect (the app reads its real `appsettings.json`/environment values correctly at normal startup) and doesn't affect any running deployment, but it is a real code characteristic worth knowing: nothing downstream of host build can change JWT signing config for this service without an app restart. It caused 33/40 integration tests to fail with 401s (every minted test token was signed with a key the app never validated against) until the tests were changed to sign with the app's real config values instead — documented in `LendingServiceApiFactory.cs`.

### 8.4 Backend: a user can reserve the same book more than once (no duplicate-pending check)
**File:** `services/lending-service/Controllers/ReservationsController.cs` (`ReserveBook`, lines 345–428)
**Found in:** Selenium E2E testing — `TC_RESERVE_EDGE_002` in `tests/selenium-tests/LendingService.Selenium/ReserveBookEdgeCaseSeleniumTests.cs` (see `final_selenium_test_results.md`)
**Severity:** Low/Medium — not a crash or data-integrity break, but a real gap in reservation fairness

`ReserveBook` checks the book's `AvailableCopies` and the caller's JWT, but never checks whether the same user already has a `Pending` reservation for the same `BookId`. Nothing in the database schema enforces uniqueness either (no unique index on `(UserId, BookId)` for pending reservations). A user can call `POST /api/reservations` for the same book any number of times while their earlier request is still awaiting admin action, producing multiple independent pending rows for one book.

**Reproduction:** log in as a regular user, reserve the same available book twice in a row (no page reload needed between attempts) → both succeed, and "My borrowings" shows two separate pending rows for the same title.

**Impact:** a single user could pin multiple copies of a popular book in "Pending" simultaneously, starving other users during the window before an admin accepts/rejects, and admins see duplicate rows in the pending queue for what is really one person's interest in one book.

**Status:** **not fixed** — out of scope for this QA pass (a code change, not a test). Recommended fix: add an `AnyAsync` check for an existing `Pending`/`Accepting` reservation by the same `UserId` for the same `BookId` before creating a new one, returning `409 Conflict` if one exists.

### Not a defect: 409/503 responses under concurrent Accept load
Called out explicitly since it involves error responses: the 60× `409 Conflict` and 20× `503 Service Unavailable` seen in the JMeter run (§7) are `ReservationsController.Accept`'s optimistic-concurrency check and Inventory Service's `AvailableCopies` concurrency token working exactly as designed under deliberately-contended concurrent load. This is correct behavior, not a bug.

### Test-harness / local-environment issues (not application defects)
Listed for completeness — these were bugs in the *test code* or local dev setup, not in `lending-service` or the frontend, so they're not counted as application defects above:
- Selenium base class: a JS native-input-setter script read a property descriptor off the wrong JS realm's prototype, throwing `Illegal invocation` — fixed in test code by walking the element's own prototype chain.
- `AdminReservationHistorySeleniumTests`: asserted on the DOM immediately after `SelectByText()`, before React's async state update had actually committed — a test-code race condition, fixed with an explicit `Wait.Until` for a stable end state.
- Local `frontend/.env` was missing, so a locally-run frontend silently called the deployed Azure API instead of `localhost` — a local dev-environment setup gap, not a code defect.
